# 产品决策记录（ADR）

> 对应 docs/product-analysis-and-recommendations.md 中的季度级战略项。记录「做 / 不做 / 何时重评」以及理由，避免反复讨论。

---

## ADR-001：摄像头录制回放 —— 本期不做（Defer）

- **状态**：不做，保持「实时预览」能力边界。
- **依据**：README/14-设备管控能力规划.md 估算 8–12 人天（FFmpeg HLS 常驻录制 + 时间轴回放 + 存储清理），是 8 项管控中唯一重工程项；当前用户价值集中在「保号 + 下载」，摄像头属于边缘场景。
- **风险**：用户误以为有历史录像。检查 README/00-项目总览.md 与 README/08-设备监控.md，现有表述均为「RTSP 实时预览」，未承诺录制，**无需改文案**。
- **重评条件**：① 出现 ≥3 个独立用户明确要求回放；② 核心链路（站点激活率/告警触达）达到目标且团队有 2 周富余；③ 或找到低维护成本的替代（直接接 NVR 的 HTTP API 而非自建 FFmpeg 录制）。

## ADR-002：多用户 / RBAC —— 不做（Hold）

- **状态**：保持单用户 + 全局配置模型。
- **依据**：文档明确站点/下载器/订阅为全局表、不按账号归属，且已有账号后禁止自助注册第二个账号。这是自托管单家庭场景的合理简化；引入多租户需要给 30+ 张表加 owner_id 并重写所有 Oper 查询，属于架构级改造。
- **风险**：无法做 hosted/SaaS 或家庭多成员隔离。
- **缓解**：把「用户偏好」与「业务配置」继续保持解耦（现状已如此），为未来迁移留缝；公网部署通过 OIDC/SSO 与强密码控制访问，而不是伪造多用户。
- **重评条件**：出现明确的多成员隔离需求，或决定提供托管服务。届时应先做数据模型可行性 spike，再决定是否重写。

## ADR-003：匿名遥测 —— 不默认开启（Reject by default）

- **状态**：不引入自动上报；不做隐式数据外传。
- **依据**：产品定位是自托管、隐私敏感（站点 Cookie/API Key 加密存本地）。任何「默认开启、用户不知道」的遥测都会破坏信任，且不符合 AGPL 自托管用户的预期。
- **替代方案**：① 在「设置 → 关于」提供**显式**的「复制诊断信息」按钮（脱敏：版本/平台/站点数量/失败计数，不含 Cookie/URL/用户名），用户自行粘贴到 issue；② 用 GitHub Discussions/Issue 模板收集使用反馈；③ 维护者定期做公开的用户访谈。
- **重评条件**：若未来要做，必须是 opt-in、字段公开可审计、可在 UI 一键关闭，并经社区讨论同意。
