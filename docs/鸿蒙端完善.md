# 鸿蒙（HarmonyOS）端完善纪要

> 2026-08 鸿蒙端专项完善的完整记录：架构决策、插件矩阵、构建流程、踩坑档案。
> 日常构建只看 §4「构建与发版」；排错先查 §5「踩坑档案」。

## 1. 架构总览

鸿蒙端沿用项目既定路线走到底，不引入第三个客户端代码库：

```
┌─ 鸿蒙端（mobile/ohos/ + Flutter 业务代码复用）
│  ① ArkTS 壳层：EntryAbility + FlutterAbility + 权限/签名（ohos/）
│  ② 引擎层：华为 Flutter 鸿蒙化分支（D:\SDK\flutter_ohos_341，3.41.10-ohos）
│  ③ 插件层：CPF-Flutter（原 openharmony-sig）社区适配分支 + 本项目 vendor 机制（§3/§4）
│  ④ 能力抽象层：lib/core/platform/（平台差异唯一收敛点，见 §2）
│  ⑤ 业务层：features/ + api/ 全量复用，零鸿蒙特判散落
└─ Go 后端（不动）：REST/WS + go:embed Vue3 Web UI ← 浏览器直连即全功能兜底
```

核心原则：

- **ArkTS 只做壳**。业务逻辑一行不写 ArkTS——它无法复用到其它 5 个平台。
- **平台差异收敛到 `lib/core/platform/`**。业务代码不允许出现
  `TargetPlatform.ohos` 或 `Platform.operatingSystem == 'ohos'` 判断。
- **鸿蒙构建是「切换式」的**（见 §4），日常 Android/iOS/桌面/Web 构建
  的依赖与源码完全不受影响（analyze + test 全绿为证）。

## 2. 能力抽象层（lib/core/platform/）

| 文件 | 职责 |
|------|------|
| `platform_caps.dart` | `isOhosPlatform` / `currentUpdatePlatform()` / `supportsInAppOta()`。鸿蒙判定用 `Platform.operatingSystem == 'ohos'`（运行时字符串），**绝不引用 `TargetPlatform.ohos`**（fork 独有枚举，官方 SDK 编译期报错） |
| `file_picker.dart` | 文件选择门面：`appFilePicker.pickFiles/saveFile` + 中立类型 `PickedFile`。业务统一 import 此文件 |
| `file_picker_default.dart` | 默认实现：转发 pub.dev file_picker 8.x |
| `file_picker_ohos_impl.dart` | 鸿蒙实现：转发 file_picker_ohos 10.3.8。与默认实现类同名（`PlatformFilePickerImpl`），构建脚本以文件替换方式切换，import 零改动 |

修复记录：`update_checker.dart` 原用 switch 处理平台，鸿蒙落 `default` 被当
Android——鸿蒙端会拿到 APK 直链尝试应用内安装，HarmonyOS NEXT 不兼容 APK
必然失败。现统一走 `platform_caps`：

- 更新检查平台键：鸿蒙 = `'ohos'`（`update-manifest.json` 的 `targets.ohos`），
  后端对未知 key 只是不回填下载信息、提示外链兜底，不报错。
- OTA：鸿蒙不支持应用内安装（系统无此 API），与桌面/iOS 同走
  `url_launcher` 外链浏览器下载。
- Web 端平台键从 `'android'` 改为 `'docker'`（Web 即后端 UI 自身，
  检查后端版本语义更正确）。

### 日常构建（一条命令）

```powershell
powershell -ExecutionPolicy Bypass -File scripts\build_ohos.ps1
```

脚本自动完成（详见脚本头注释）：

1. 套用 `pubspec_overrides.ohos.yaml` → `pubspec_overrides.yaml`
2. 切换 file_picker 实现（`file_picker_default.dart` ← ohos 实现，同名类）
3. 主 pubspec 追加 `file_picker_ohos`（锚点块 `OHOS-ONLY-DEPS`）
4. `flutter pub get`（ohos SDK，解析 9 个 ohos 插件）
5. **vendor**（`scripts/vendor_ohos_plugins.ps1`）：把每个插件的 `ohos/`
   目录从 pub 缓存复制到 `mobile/ohos/plugins/<name>/ohos`——hvigor 6 的
   ArkTS 编译器无法为项目根之外的源码生成 OhmUrl（§5 #9），vendor 进来
   后由 ohos/build-profile.json5 里手工声明的插件 modules 接管编译
6. `flutter build hap --release`（脚本内设 DEVECO_SDK_HOME + ohpm PATH；
   成功判定用「HAP 是否新鲜产出」而非退出码，§5 #13）
7. **无条件复原** 1-3（finally 保证）

产物：

```
mobile/ohos/entry/build/default/outputs/default/entry-default-unsigned.hap（约 65MB）
```

构建成功标志：`GeneratedPluginRegistrant.ets` 里 9 个插件 import + 注册
调用齐全（改造前是空的 = 无任何原生插件）。

**vendored 插件的三处配套**（缺一不可，改插件集时同步）：

1. `scripts/vendor_ohos_plugins.ps1` —— 复制（幂等，每次构建刷新）+
   把 vendored 插件的 hvigorfile.ts 统一重写为「从 hvigor 运行时缓存取
   harTasks」（原版裸 re-export 在 vendored 位置解析不到，§5 #9）
2. `mobile/ohos/build-profile.json5` 的 `modules` 段 —— 每个插件一条
   `{"name": <pkg>, "srcPath": "./plugins/<pkg>/ohos", …}`
3. ohos fork 的 TS hvigor 插件（`packages/flutter_tools/hvigor/src/plugin/
   flutter-hvigor-plugin.ts`）已打本地补丁：`findFlutterPlugins` 结果优先
   重定向到 `ohos/plugins/<name>`（vendored 副本）

### 签名

两条路，按用途选：

**A. 本地自签（模拟器/自己的设备测试）**——`signing/generated/` 里的
OpenHarmony 自签材料（keystore 口令 `123456`，alias `pt-app-key`）：

```bash
cd mobile/ohos/signing/generated
java -jar "D:\SDK\harmonyos-sdk\HarmonyOS-6.1.1\openharmony\toolchains\lib\hap-sign-tool.jar" \
  sign-app -mode localSign -keyAlias pt-app-key -keyPwd 123456 \
  -appCertFile app-release-cert-chain.cer \
  -profileFile ptpatronus-release-profile.p7b -profileSigned 1 \
  -inFile <构建产出的 entry-default-unsigned.hap> \
  -signAlg SHA256withECDSA \
  -keystoreFile ptpatronus-signing.p12 -keystorePwd 123456 \
  -outFile <签名输出.hap>
```

p12 别名清单：`keytool -list -keystore ptpatronus-signing.p12 -storetype
PKCS12 -storepass 123456`（pt-app-key / pt-app-ca / pt-profile-key /
pt-profile-ca / pt-root-ca 五个，**签名用 pt-app-key**，用错别名报
"ensure keyAlias is exist"）。

**B. 官方签名（发版上架）**：`mobile/ohos/signing/sign-official-hap.ps1`
（需先 `import-official-signing.ps1` 导入华为官方 p12/p7b）。

## 5. 踩坑档案（全部实证，按价值排序）

1. **TargetPlatform.ohos 编译炸弹**：ohos 生态包常引用 fork 独有枚举
   `TargetPlatform.ohos`，官方 stable SDK 编译期 "Member not found"。
   chewie 用常驻 override 锁 1.12.1；inappwebview 锁历史 commit；
   自研代码一律用 `Platform.operatingSystem == 'ohos'` 运行时判断。
2. **分支版本字段错位**：适配分支名里的版本 ≠ 包 pubspec version（见 §3）。
   引用前必须 `git show <ref>:…/pubspec.yaml` 核实，否则 pub 报
   "Package not available"。
3. **file_picker web 依赖死结**：适配版 10.3.8 改名 `file_picker_ohos`、
   依赖 web ^1.0.0，无法 override 替换 file_picker；8.x ohos 分支（保持
   原名）锁 web ^0.5.1，与 share_plus 鸿蒙分支的 web ^1.0.0 冲突，pub
   无解。→ 独立依赖 + 门面切换（§2/§4）。
4. **pubspec_overrides.yaml 字段限制**：只允许 dependency_overrides/
   resolution/workspace，新增依赖必须动主 pubspec（脚本锚点块方案）。
5. **PowerShell 5.1 两炸**：(a) UTF-8 无 BOM 的中文 .ps1 被 GBK 解析语法
   错——所有中文脚本必须 BOM；(b) `& bat 2>&1 | 管道` 会把 stderr 包装成
   ErrorRecord 令 flutter 工具崩溃——用 `cmd /c` 整体捕获。
6. **Git LFS 断链**：CPF-Flutter 多个仓库 example/ 塞了 LFS 大文件且远端
   缺对象（inappwebview 的 icudtl.dat、video_player 10.x 的 mp4、chewie 的
   AssetManifest.bin），pub 克隆必炸。全局 `git-lfs smudge --skip` 后克隆
   通过（指针文件留在 example/ 无害）；chewie 干脆 sparse checkout 只留
   lib+pubspec 存到 D:\SDK\chewie_ohos 以 path override 引用。
7. **Node 24 × pnpm 7**：hvigor wrapper 的 `spawnSync(pnpm.cmd, args)` 在
   Node ≥20.12 抛 EINVAL（CVE 修复行为）。wrapper pnpm 升 9.15.9 解决；
   另 hvigor-wrapper.js 的 executeCommand 在 Windows 上需 shell 拼串调用
   （已本地补丁）。
8. **sdk-pkg.json UTF-8 BOM**：华为 SDK 的 sdk-pkg.json 自带 BOM 时，
   fork 工具链 JSON5 解析失败 → "No Hmos SDK found"。去 BOM 即可。
9. **hvigor 6 OhmUrl 项目外源码死结**（本轮最大坑）：ArkTS 编译器
   （rollup+es2abc）无法为项目根之外的文件（pub 缓存里的插件 ohos/）生成
   OhmUrl，报 "Failed to resolve OhmUrl"；顺带的 sourcemap 崩溃
   `Cannot read properties of undefined (reading 'split')` 同根因。
   → vendor 机制（§4）：插件复制进 `ohos/plugins/`、build-profile 声明
   modules、TS 插件路径重定向 + vendored hvigorfile 重写，四件套。
10. **API18 死路**：hvigor 5.19.8（最高 API19）编译时引擎 har 自身引用
    `GlobalWindowMode`/`isCapsLockOn` 等 API>19 接口 → ArkTS 报
    "Property does not exist"。引擎 har 与 API24 绑死，hvigor 6 必选，
    别再尝试降 API。
11. **`dart.library.ohos` 条件导入恒假**：3.41 fork 的 sky_engine 未导出
    该 library，社区写法在本仓库不成立。平台分支只能收敛到运行时判断
    （platform_caps）或构建期切换（file_picker 门面）。
12. **build-profile 模式差异**：HarmonyOS runtimeOS 下 SDK 版本必须是
    `"6.1.1(24)"` 字符串格式；OpenHarmony 模式才是数字。schema 报错时
    先看格式再看数值。
13. **flutter.bat 退出码误报**：`cmd /c` 包装下 build hap 成功（HAP 已产
    出、hvigor 打印签名提示）但退出码为 1（Windows errorlevel 传递怪癖）。
    脚本以「HAP 文件在构建窗口内新鲜产出」为成功判据。
